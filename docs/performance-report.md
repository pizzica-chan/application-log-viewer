# インデックス構築・検索の性能調査レポート

対象: application-log-viewer（aplv） / MyBatis-log-viewer（mlv）
測定日: 2026-09-06 〜 2026-09-08
測定環境: Windows 11 / 12 論理コア / JDK 8 ターゲット / sqlite-jdbc 3.46.1.3
計測条件: `-Xmx2g`（1GB 級のログのみ `-Xmx3g`）、`tmp` は同一ドライブ

---

## 1. 要約

| | 対象 | 結果 |
|---|---|---|
| aplv 検索 | 1ページ目の応答 | 3,805ms → **22ms**（160万件） |
| aplv 構築 | 423MB / 300万件 | 中央値 15.5→**10.7**秒 / 16.3→**11.8**秒（28〜31% 短縮、3.7 節） |
| aplv DB | 同上 | 631MB → **566MB**（10% 削減） |
| mlv 構築 | 1084MB / 250万 SQL | 38.4秒 → **34.5秒**（約 10% 短縮） |
| mlv DB | 同上 | 834MB → **813MB**（2.5% 削減） |

最大の学びは **「同じ最適化が別アプリでは逆効果になった」** こと、そしてその原因が
行数や行幅ではなく **パイプラインのどちらが律速か** だったことである（→ 第5章）。

## 2. 計測方法

推測を避けるため、以下を原則とした。

1. **本番経路で測る** — `openOrCreate` + `buildIndex` を実際に呼ぶベンチを書く。
   スキーマだけ自前で組む版も用意し、索引の有無を切り替えて分解計測できるようにした。
2. **変更前後を同一データで測る** — `git worktree` で変更前の HEAD をビルドし、
   同じログファイルに対して交互に実行する。
3. **結果の同一性を確認する** — 新旧サーバを同時起動し、API 応答を突き合わせる。
4. **実行計画を見る** — `EXPLAIN QUERY PLAN` で索引選択と並べ直しの有無を確認する。

### ボトルネックの判定方法

**同じログ量をファイル数だけ変えて比較する。** パースは複数ファイルを並列処理し、
SQLite への書き込みは単一スレッドに集約されるため、ファイル数を増やして速くなれば
パース律速、変わらなければ書き込み律速と判定できる。

## 3. application-log-viewer

### 3.1 検索の遅さ（SQL 押し下げ）

**問題**: 全ヒットを `ResultSet` から Java オブジェクトに起こして件数を数え、
`offset`/`limit` を Java 側で適用していた。ヒット件数に比例した時間がかかる。

**対処**: 正規表現・grep がいずれも未指定なら、件数を `COUNT(*)`、ページを
`LIMIT/OFFSET` で SQL に任せる。

**結果**（160万件のインデックス、200件/ページ）:

| ケース | 前 | 後 |
|---|---|---|
| 全件 1ページ目 | 3,805ms | **22ms** |
| INFO 1ページ目 | 3,729ms | **39ms** |
| ERROR 1ページ目 | 108ms | **6ms** |
| ERROR 深い offset | 120ms | **6ms** |
| ERROR + 期間 | 77ms | **5ms** |
| WARN,ERROR | 398ms | **143ms** |

### 3.2 レベル絞り込みの並べ直し

`ORDER BY ts_millis` に対して SQLite が `idx_entries_level` を選ぶと、
ヒット全件を並べ直してから `LIMIT` を適用してしまう。3案を比較した（200万行）。

| ケース | 現状 | ANALYZE のみ | 複合索引 + ANALYZE |
|---|---|---|---|
| ERROR 1ページ目 | 93ms | 4ms | **3ms** |
| INFO 1ページ目 | 357ms | 0ms | **0ms** |
| ERROR 深い offset | 117ms | **254ms** ⚠ | **3ms** |
| 該当0件のレベル | 0ms | **318ms** ⚠ | **0ms** |
| ERROR + 期間 | 82ms | 2ms | **0ms** |

**`ANALYZE` 単体は安いが退行を伴う。** 統計だけ入れると全件走査を選ぶようになり、
深い offset とヒット0件で逆に遅くなる。複合索引 `(level, ts_millis, file_id, line_no)`
を足すと全ケースで速くなり退行がない。

### 3.3 冗長な索引の削除

複合索引の先頭列が `level` なので、`idx_entries_level(level)` は代替可能。
削除すると構築が速くなるだけでなく、**クエリも速くなった**。
幅の狭い索引が残っていると SQLite がそちらを選び、並べ直しが入るため。

| | 索引あり | 索引なし |
|---|---|---|
| 索引構築 | 4.82秒 | **3.25秒** |
| DB サイズ | 606MB | **566MB** |
| WARN,ERROR 1ページ目 | 331ms（`idx_entries_level` + SORT） | **17ms** |

### 3.4 構築のボトルネック特定

423MB / 300万件で、**単一ファイル 15.79秒・8ファイル 16.59秒とほぼ同じ**だった。
パースは並列化済みなので、律速は SQLite への書き込み側と判明。

分解計測（page_size 既定 4096）:

| | 取込 | 索引 | ANALYZE | 合計 | DB |
|---|---|---|---|---|---|
| 索引を取込中に維持 | 16.28秒 | — | 1.78秒 | 18.06秒 | 631MB |
| 索引を取込後に一括作成 | 7.40秒 | 6.18秒 | 1.40秒 | 14.98秒 | 615MB |
| 索引なし | 7.09秒 | — | 0.35秒 | 7.45秒 | 439MB |

行ごとの B-tree 更新が **9.2秒**、一括作成なら **6.2秒**。

### 3.5 PRAGMA のチューニング

**page_size**（索引は取込後に作成）:

| page_size | 取込 | 索引 | ANALYZE | 合計 |
|---|---|---|---|---|
| 4096（既定） | 7.88秒 | 6.61秒 | 1.52秒 | 16.01秒 |
| 8192 | 6.59秒 | 5.36秒 | 1.33秒 | 13.28秒 |
| **16384** | 6.24秒 | 5.01秒 | 1.44秒 | **12.69秒** |
| 32768 | 7.21秒 | 5.27秒 | 1.49秒 | 13.97秒 |

**analysis_limit**（`ANALYZE` が走査する行数の上限）:

| 設定 | ANALYZE | 合計 |
|---|---|---|
| 無制限 | 1.55秒 | 13.53秒 |
| 400 | 0.04秒 | 12.07秒 |
| **1000** | 0.04秒 | **11.61秒** |

**ただしサンプリングは統計の精度を落とす。** 低カーディナリティな先頭列では
「1 値あたりの行数」が `analysis_limit + 1` の定数になり、実データを反映しない。
値を上げても定数が変わるだけで精度は上がらない。

| 索引（先頭列） | 完全 ANALYZE | limit=100 | limit=1000 | limit=10000 |
|---|---|---|---|---|
| `level`（aplv・200万行） | 500000 | — | **1001** | — |
| `mapper`（mlv・50万行） | 62500 | 101 | **1001** | 10001 |
| `sql_type`（mlv・50万行） | 125000 | 101 | **1001** | 10001 |
| `ts_millis`（高カーディナリティ） | 1 | 1 | 1 | 1 |

それでも採用しているのは、**歪みがプラン選択を変えるかどうかは索引構成しだい**で、
aplv では変えないため。時刻順に辿れる索引が用途ごとに 1 本ずつしかなく競合しない。
200万行で 7 種のクエリ形状すべてについて、実行計画・実行時間が完全統計と一致した。

mlv は事情が異なり、`idx_entries_elapsed` が `idx_entries_type_ts` と競合するため、
`sql_type` + `elapsed_ms` の COUNT で計画が分かれる（どちらが速いかはデータ分布しだい）。
一覧・ページングの主要な形状は一致する。完全統計のコストが構築時間の約 5% にあたるため、
この偏りを許容して採用している。

**索引を増やすときは、この前提が崩れていないか `EXPLAIN QUERY PLAN` で確認すること。**

### 3.6 採用しなかったもの

| 案 | 測定結果 | 判断 |
|---|---|---|
| `cache_size` 増（64→128→256MiB） | 13.72 / 13.53 / 13.17秒 | 誤差レベル。メモリを使う価値なし |
| `journal_mode = OFF` | 11.00秒 vs MEMORY 11.91秒 | 再現しない差。耐障害性の議論を招くだけなので不採用 |
| `entries(file_id, line_no)` 索引 | — | UI が必ず timestamp を送るため到達しない経路のためのコスト |

### 3.7 最終結果（本番経路・変更前後を交互に3回）

| | 前（最小〜最大 / 中央値） | 後（最小〜最大 / 中央値） | 短縮 |
|---|---|---|---|
| 単一ファイル | 15.38〜15.82 / **15.52**秒 | 10.57〜11.19 / **10.67**秒 | −31% |
| 8ファイル | 16.18〜17.67 / **16.30**秒 | 10.97〜11.97 / **11.75**秒 | −28% |
| DB サイズ | 631 / 641MB | **566 / 573MB** | −10% |

コスト: 複合索引を 1 本足したぶん、索引更新込みの INSERT が 200万行あたり
5.9秒 → 7.7秒（+1.8秒）、DB が 255MB → 308MB（+21%）。差し引きで上表の短縮となる。

## 4. MyBatis-log-viewer

### 4.1 そのまま移植したら遅くなった

aplv の変更一式（page_size + 索引の後付け + analysis_limit）を移植したところ、
**216MB / 50万 SQL で 6.2秒 → 7.6秒**と約 23% 悪化した。

### 4.2 分解計測

| 216MB / 50万件 / 索引4本 | 取込 | 索引 | 合計 |
|---|---|---|---|
| 索引なし | 6.08秒 | — | 6.08秒 |
| 索引を取込中に維持 | 5.85秒 | — | **5.85秒** |
| 索引を取込後に一括作成 | 5.71秒 | 1.19秒 | 6.90秒 |

索引維持のコストがほぼ無く、一括作成は 1.19秒 かかるため、後付けは負ける。

> **この表は単発測定で、後にばらつきの大きさが問題になった。** 「索引なし 6.08秒」が
> 「索引を維持 5.85秒」より遅いのは物理的にありえず、この規模で 0.2〜0.3秒 の
> ばらつきが乗っていることを示している。結論（一括作成を採らない）は 2 案の差が
> 0.9秒 あるので揺るがないが、個々の数値を精度のあるものとして引用してはいけない。
> パーサ最適化後に 7 回ずつ測り直した値は 4.4 節に載せた。

### 4.3 採用したもの

| 変更 | 効果 |
|---|---|
| `analysis_limit = 1000` | `ANALYZE` が 1.94秒 → **0.13秒**（250万件） |
| `ensureStatistics` 廃止 → 毎回 `updateStatistics` | 索引構成の変更で古くなる統計を解消。上記で安くなったため可能に |
| `page_size = 16384` | 構築時間はほぼ横ばい、DB が **2.5% 削減**（834MB → 813MB） |

**結果**: 1084MB / 250万 SQL で 38.4秒 → **34.5秒**。

### 4.4 見送ったもの

- **索引の取込後一括作成** — 50万件で 6.2→7.6秒、250万件でも 34.5→35.6秒と一貫して悪化。
  パーサ最適化で書き込み律速に移ったあとも変わらない。50万件・1ファイルで各 7 回測ると
  中央値は 索引なし 3.39秒 / 取込中に維持 3.67秒 / 取込後に一括 4.50秒。
  この規模では索引 B-tree がページキャッシュ（約 64MiB）に収まるため行ごとの維持は
  +0.28秒 で済む（ばらつき幅 0.25秒 と同程度なので精度は低い）のに対し、
  一括作成は幅の広い表を索引 4 本ぶん走査するため +0.83秒 かかる（範囲が重ならず明確）
- **一覧 `raw` の切り詰め** — `MAX_LIMIT` の既存コメントに
  「raw を切り詰めるとハイライトとずれるため上限側で抑える（5000件で 5.2MB 実測）」
  と実測付きの判断が既にあり、`MAX_LIMIT=1000` で対処済みのため踏襲

## 5. なぜ同じ最適化で結果が逆になったのか

### 5.1 主因: パイプラインのどちらが律速か

> **以下はパーサ最適化（4.4 節）より前の状態の記録。** その最適化で mlv は書き込み律速へ
> 移り、索引を取込中に維持する理由も「パース律速で隠れるから」ではなく
> 「この規模では B-tree がページキャッシュに収まるから」に変わった。
> 現在の説明は 4.4 節と `SqlLogIndex.initSchema` のコメントを参照。

同じログ量をファイル数だけ変えて、索引なしの取込を比較した。

| （最適化前） | 1ファイル | 8ファイル | 判定 |
|---|---|---|---|
| aplv（300万件） | 7.09秒 | 7.02秒 | **書き込み律速** |
| mlv（50万件） | 5.60秒 | **2.28秒**（2.5倍） | **パース律速** |

aplv のパーサは「1行 = 1エントリ」でバイト列の事前判定も入っており軽い。
対して mlv は Preparing / Parameters / Total の **3行を1ブロックに組み立てる**うえ、
正規表現とパラメータ抽出が入り、1エントリあたり約 5 倍重い。

当時の説明はこうだった。**書き込みスレッドに余力があるうちは、索引維持のコストは
隙間に隠れてタダになる。取込後の一括作成はその余力を使えず、純粋な直列の追加時間になる。**

この説明はパーサ最適化で反証された。書き込み律速へ移ったあとも 1 ファイルでの
索引維持は +0.28秒 にとどまり、「隠れていたコストが露出する」という予測どおりには
ならなかった（8 ファイル時は +1.57秒 と露出したので、規模の問題だった）。
現在の説明は 4.4 節のとおり。

### 5.2 検証: 律速を変えると符号が反転する

mlv で同じ 50万件をファイル数だけ変えると、隠れていた索引維持コストが露出する。

| mlv 50万件 | 索引なし | 取込中に維持 | 取込後に一括 |
|---|---|---|---|
| 1ファイル（パース律速） | 6.08秒 | **5.85秒**（維持 ≒ 0） | 6.90秒 |
| 8ファイル（書き込み律速） | 2.54秒 | 4.11秒（維持 1.57秒） | **4.07秒** ← 拮抗 |

さらに行数を上げると、単発では逆転したように見えた。

| mlv 8ファイル・240万件（単発） | 索引なし | 取込中に維持 | 取込後に一括 |
|---|---|---|---|
| | 8.72秒 | 16.79秒（維持 8.07秒） | 16.16秒 |

> **この行も後に各 10 回測り直した。** 中央値は 維持 16.94秒 / 一括 16.43秒（差 3%）で
> 分布が大きく重なり、**優劣は判定できなかった**。単発では「一括が 4% 勝つ」と読めたが、
> その差は測定のばらつきに埋もれる。試したどの規模でも一括が有利という証拠は無い。

### 5.3 副次要因

- **行数** — 書き込み律速でも行数が少なければ拮抗する（50万件で 1.57 vs 1.43秒）。
  行数が増えると索引 B-tree がページキャッシュ（64MiB）を超えて逐次更新が悪化するため、
  ソートベースの一括作成が有利になっていくと考えられる。ただし 240万件で測り直した
  範囲では、その差はばらつきに埋もれて確認できなかった（5.2 節の注記）。
- **行幅** — mlv は 209 B/行、aplv は 146 B/行。一括作成は表を全走査するため、
  行が太いほど不利。同じ 240〜300万件でも、aplv は一括作成のほうが **17% 速い**
  （3.4 節の 18.06秒 → 14.98秒。ただし単発測定）のに対し、
  mlv では**有意な差を確認できなかった**（5.2 節の注記）。

### 5.4 追記 — パーサ側を削ると律速は移る

主因がパースだと分かったので、mlv のパーサを詰めた。ヘッダ行の解析で
スレッド判定の正規表現（`THREAD_HINT`）を 2 回無条件に実行していたが、
`^main(?:$|:)` 以外のすべての選択肢は `-` を含むため、**`-` が無く "main" でも
始まらない文字列は正規表現を呼ばずに不一致と判定できる**（判定結果は同一）。
FQCN の logger ではほぼ必ずこの形式に該当するため、失敗すると分かっている走査を丸ごと省ける。

| 90万行のヘッダ解析 | 時間 |
|---|---|
| 現状（`THREAD_HINT` を常に 2 回） | 1.72 秒 |
| `-` と `main` で事前判定 | **0.25 秒** |
| 正規表現を一切呼ばない（下限） | 0.15 秒 |

この 1 箇所で、`LogParser.parse` の 91% を占めていたコストが消えた。

| 索引なしの取込・50万件 | 1ファイル | 8ファイル | 判定 |
|---|---|---|---|
| 最適化前 | 6.90 秒 | 2.23 秒 | パース律速（3.1 倍） |
| 最適化後 | 3.50 秒 | 2.12 秒 | パース律速は緩和（1.65 倍） |

索引込みの構築では **6.49 秒 → 3.93 秒（39% 短縮）** となり、8 ファイル時（3.85 秒）と
同水準に達した。つまり **mlv は書き込み律速に移り、これ以上パーサを削っても
構築時間は縮まない**。

> この 6.49 秒は上の表（索引なしの取込 6.90 秒）とは別セッションの測定で、索引を作るぶん
> 本来は遅くなる。単発測定に 0.2〜0.5 秒 のばらつきが乗るため逆転して見えるだけなので、
> 表と本文の値を引き算しないこと。

aplv にも同じ最適化を入れたが、元から書き込み律速なので構築時間は変わらない
（11.4〜12.3 秒 → 11.0〜11.5 秒で誤差の範囲）。CPU は減るので入れてある。

**律速は最適化で移動する。** 一度判定したら終わりではなく、効いたあとに測り直す。

### 5.5 結論

> **「索引は取込後にまとめて作る方が速い」は無条件の定石ではない。**
> 書き込みが律速で、かつ行数が多いときにだけ成立する。
> パースが律速なら索引維持はタダなので、後付けは必ず損になる。

## 6. 一般化できる指針

1. **最初にボトルネックを特定する。** 同じ入力をファイル数だけ変えて測れば、
   パース律速か書き込み律速かが一発で分かる。ここを飛ばすと、効かない場所を
   最適化して悪化させる（実際に mlv で 23% 悪化させた）。
2. **移植先で測り直す。** 姉妹プロジェクトで効いた手法（索引の取込後一括作成、単独で
   17% 短縮）が、別プロジェクトでは逆効果だった。コードが似ていても律速が同じとは限らない。
3. **統計は入れるだけでは足りない。** `ANALYZE` 単体では退行するケースがあり、
   索引と組み合わせて初めて全ケースで速くなる。実行計画まで確認する。
   `analysis_limit` によるサンプリングは低カーディナリティ列の統計を定数に潰すため、
   「安いから入れておく」ではなく、索引構成ごとに影響を確認して採否を決める。
4. **冗長な索引は構築だけでなく検索も遅くする。** 幅の狭い索引が残っていると
   プランナがそちらを選び、並べ直しが発生することがある。
5. **性能に関するコメントは測ってから書く。** この調査中、実測と食い違う説明を
   4回書いてレビューで指摘された（複数レベルの実行計画、page_size の効果、
   mlv で後付けを見送った理由、analysis_limit の精度）。推測を断定形で書かない。
6. **判断の根拠にする数値は複数回測る。** 数百 MB 規模では 1 回の測定に数 % の
   ばらつきが乗る。単発の差がその範囲に収まるなら「差はない」と書く。試行回数と
   代表値（中央値か最小値）を添えれば、後から読む人が精度を見積もれる。
7. **既存コメントに記録された判断を確認する。** mlv では `raw` の切り詰めが
   実測付きで既に否定されていた。理由なく覆さない。

## 9. ログ書式の追加が性能に与える影響（2026-09-13）

書式を 1 つに確定させてから取り込む設計（`LogFormat`）を入れたときの計測。
**結論: 書式を増やしても取り込み性能は変わらない。**

### なぜ変わらないか

同時に取り込むファイルはすべて同じ書式という前提を置き、**取り込み開始時に書式を
1 つへ確定させている**。そのため 1 行あたりに走る判定は確定した 1 書式ぶんだけで、
書式の分岐は switch のジャンプ表 1 回に収まる。書式を N 個に増やしても
1 行あたりの処理は N 倍にならない。

### 実測

計測条件はいずれも Windows 11 / 12 論理コア / `-Xmx2g`、変更前後の jar を
同一データに対して交互実行。差はすべて 1 回の測定のばらつきの内側で、
解析結果（ヘッダ判定数・解析成功数）は完全に一致している。

| 対象 | データ | 変更前（中央値） | 変更後（中央値） | 差 | ばらつき幅 |
|---|---|---|---|---|---|
| aplv 取り込み全体 | 239MB / 180万行 | 5,790ms（12 回） | 5,936ms（12 回） | +2.5% | 23〜31% |
| aplv パース単体 | 同上 | 935ms（5 回） | 940ms（5 回） | +0.5% | 4〜5% |
| mlv パース単体 | 216MB / 160万行 | 812ms（7 回） | 833ms（7 回） | +2.6% | 8〜13% |
| alv パース単体 | 163MB / 150万行 | 2,416ms（7 回） | 2,427ms（7 回） | +0.5% | 6〜9% |
| aplv パース単体（書式を 4→5 に追加） | 239MB / 180万行 | 1,014ms（7 回） | 986ms（7 回） | −2.8% | 17〜22% |

自動判定（先頭ファイルの冒頭 500 行をサンプリング）は 0〜16ms（初回のクラスロード込み）で、
取り込み 5〜6 秒に対して無視できる。

### 差は行数に比例するか

「ログが増えるほど誤差になるのか」を確かめるため、同じ変更をサイズ違いで測った。

| ログ量 | 変更前 | 変更後 | 差 | 1 行あたり |
|---|---|---|---|---|
| 18万行 | 150ms（9 回） | 156ms（9 回） | +4.0% | +33 ns/行 |
| 180万行 | 932ms（9 回） | 945ms（9 回） | +1.4% | +7 ns/行 |

行数を 10 倍にしても差は 10 倍にならず（+6ms → +13ms）、1 行あたりに換算した値は
33ns → 7ns と**下がる**。純粋な行あたりコストなら 1 行換算値は一定になるはずなので、
実測されている差は行数に比例する成分ではなく固定費（JIT のウォームアップ等）が
支配的と考えられる。ただし比例成分がゼロだと示したわけではなく、
**この規模の測定分解能（4〜6%）を下回っていて区別できない**、というのが正確なところ。

### 新しい書式を足すとき

- 1 行あたりの判定は 1 書式ぶんという前提を崩さない（行ごとに複数書式を試さない）
- 既定書式の経路が変わっていないことを、パース単体で変更前後を交互に測って確認する
- 書式どうしが取り違えられないことを試験で押さえる（`LogFormatTest`）

## 10. 生ログ読み出しの高速化（2026-09-21）

セッション追跡（`--fts` なし）が 5 秒台だったため、内訳を測って原因を特定した。
一覧の全文検索（grep）も同じ経路を通るので、あわせて直した。

### 10.1 内訳（100 万行・108 MB・1 ファイル、Windows 11 / JDK 8、3 回の中央値）

| 処理 | 時間 |
|---|---|
| SQL で行を取り出すだけ（生ログを読まない） | 2,262ms |
| 現状（エントリごとに seek + read + UTF-8 デコード + 照合） | 5,221ms |
| 逐次読み + バイト列照合（実験） | 3,152ms |

行の取り出しだけで 4 割強を占めていた。さらに列を絞って測ると 1,185ms まで下がり、
**一致しない行の文字列列（logger / thread / message / パス）を作る費用**が主因と分かった。

### 10.2 採用した 3 つの変更

| 変更 | 内容 |
|---|---|
| 文字列列の遅延取り出し | 判定に要るのは byte 範囲だけ。文字列は一致した行とページに載る行でだけ取り出す。ファイルのパスは行ごとではなく file_id ごとに 1 回 |
| まとめ読み | `LogIndex.SequentialRawReader`（64 KiB の窓）。戻る要求と窓を超えるエントリは都度読むので内容は変わらない |
| バイト列照合 | セッション ID と、メタ文字を含まない grep はデコードせずに探す。UTF-8 は先頭バイトと継続バイトの範囲が重ならないので結果は同じ。grep は ASCII だけ畳む（既存の `CASE_INSENSITIVE` と同じ範囲） |

### 10.3 結果（同条件・5 回の中央値）

| 経路 | 前 | 後 |
|---|---|---|
| 追跡 `--fts` なし・起点 26 件 | 5,221ms | **577ms** |
| 追跡 `--fts` なし・起点 299 件 | 5,270ms | **587ms** |
| 追跡 `--fts` なし・起点 133,347 件 | 5 秒台 | **860ms** |
| 追跡 `--fts` あり・起点 133,347 件 | 1,008ms | **630ms** |
| 追跡 `--fts` あり・起点 26 / 299 件 | 11ms / 52ms | 11ms / 58ms（差はない） |
| grep リテラル `--fts` なし | 5,793ms | **941ms** |
| grep 正規表現 `--fts` なし | 5,678ms | **1,005ms** |
| grep ありふれたリテラル（13 万件ヒット） | 5,709ms | **663ms** |

索引の形式は変えていないので、既存の索引はそのまま使える（作り直し不要）。

### 10.4 結果の同一性

レポート 2 章の手順どおり、変更前の HEAD を `git worktree` でビルドして新旧サーバを
同時に起動し、15 通りの API 応答（grep のリテラル・大文字・日本語・3 文字未満・正規表現・
複数行、列の絞り込みとの併用、ページング、セッション追跡の 2 モードと絞り込み）を
突き合わせて全件一致を確認した。単体試験にも、リテラル経路と正規表現経路が同じ結果を
返すこと、ASCII だけを畳むこと（「あ」と「ぢ」のように UTF-8 で 0x20 しか違わない文字を
取り違えないこと）を追加した。

### 10.5 MyBatis-log-viewer への横展開

mlv の `SqlQuery.scanWithJavaFilter` も同じ作りだったので、測ってから同じ 3 点を入れた
（30 万エントリ・90 万行・141 MB の生成ログ、Windows 11 / JDK 8、3 回の中央値）。

| 処理 | 時間 |
|---|---|
| 現状の grep（本番経路・リテラル） | 2,644ms |
| 現状の grep（本番経路・正規表現） | 2,630ms |
| SQL で行を取り出すだけ | 1,263ms |
| 列を数値だけに絞る | 227ms |

行の取り出しが支配的で、そのうち 1,036ms が文字列列の生成だった。mlv は `sql_text` と
`parameters` を毎行文字列化するため、aplv より削減幅の割合が大きい。

| 経路 | 前 | 後 |
|---|---|---|
| grep リテラル | 2,644ms | **420ms** |
| grep 正規表現 | 2,630ms | **893ms** |

読み出し失敗を握りつぶしていた箇所も、aplv と同じくエラーにした。結果の同一性は、
変更前の HEAD をビルドして新旧サーバの応答 11 通り（大文字小文字・日本語・3 文字未満・
正規表現・列の絞り込み併用・ページング・grep なし）を突き合わせて確認した。

### 10.6 やらなかったこと

| 案 | 理由 |
|---|---|
| バイト位置から行を引く索引（`entries(file_id, byte_offset)`） | SQL の行取り出し（残り約 1.2 秒）を削るには要るが、索引を増やすと構築が遅くなりインデックスの作り直しも要る。3.6 節で同様の索引を見送った判断と揃える |
| 窓の大きさの調整 | 64 KiB で上の結果が出ており、変える根拠になる測定をしていない |

## 11. 利用者が定義する書式（正規表現）の性能（2026-09-21）

組み込み書式（`LogFormat`）に無いログを、利用者が `aplv-log-formats.txt` に正規表現で
定義して読めるようにしたときの計測。

**結論: 組み込み書式の速度は変わらない。利用者定義の書式は取り込み全体で +5.3% になる。**

判断の基準は「今まで読めなかったログが読めるようになり、今まで読めていたログの性能が
落ちないなら、新しい書式が組み込みより遅くても構わない」。この章はその 2 点を測った記録。

### 11.1 組み込み書式が遅くなっていないか

1 行あたりに走る判定は、従来どおり確定した 1 書式ぶんだけ。利用者定義の書式を足しても、
取り込みループで見るのは「利用者定義かどうか」の分岐 1 つで、組み込み書式では
そこから先が従来と同じ経路になる。

変更前（`d56168b`）と変更後の jar を同じログに対して交互に実行した。
Windows 11 / 12 論理コア / JDK 8 / `-Xmx2g`、103.1 MiB（108,088,268 バイト）/
100 万行 / 1 ファイル、既定書式。
`IndexStore.deleteIndexFiles` → `openOrCreate` → `buildIndex` の本番経路を呼ぶ。

| 対象 | 中央値（7 回） | 最小 | 最大 | 取り込んだ件数 |
|---|---|---|---|---|
| 変更前 | 2,964ms | 2,934ms | 3,174ms | 1,000,000 |
| 変更後（既定書式） | 2,975ms | 2,943ms | 3,065ms | 1,000,000 |

差は +11ms（+0.4%）で、ばらつき幅（変更前 8.2% / 変更後 4.1%）の内側。
**この測定では差を検出できていない**、というのが正確なところ。

索引のフィンガープリントも、組み込み書式では従来と同じ文字列（`format:<id>`）のまま。
利用者の手元にある既存の索引は作り直されない。利用者定義の書式では、id だけでなく
正規表現と日時書式も含める（定義を直したのに古い索引が使われるのを防ぐ）。

### 11.2 利用者定義の書式はどれだけ重いか

同じ内容を利用者定義の書式の並びに変換したログ（100 万行）で、同じ経路を測った。

| 書式 | ログの大きさ | 中央値（7 回） | 最小 | 最大 | 既定書式比 |
|---|---|---|---|---|---|
| 既定書式（バイト判定 + 手書きパーサ） | 108,088,268 バイト | 2,975ms | 2,943ms | 3,065ms | 1.00 |
| 利用者定義（正規表現 1 本） | 107,088,268 バイト | 3,134ms | 3,081ms | 3,190ms | **1.05** |

**この 2 行は別ファイル同士の比較**である。既定書式ではそのログを 1 行も読めないため、
同一ファイルでの比較は原理的にできない。行数（100 万）・取り込んだ件数（100 万）・
メッセージの中身は揃えてあり、**利用者定義側のログは 0.93% 小さい**（書式の並びが
短いぶん）。サイズ差は速くなる向きに働くので、+5.3% がサイズ差で水増しされている
ということはない。同一ファイルで比べられるのは、次の解析単体の測定。

### 11.3 解析だけを取り出すと 2.4 倍

取り込み全体で +5.3% に収まるのは、この工程が書き込み律速だから。解析だけを
メモリ上で回すと差はもっと大きい（100 万行、7 回の中央値、IO を外すためファイルは
先に読み込む）。**こちらは同一ファイルに両方式を適用して比較している**ので、ログの違いは入らない。

| 方式 | 継続行なし（103.1 MiB） | 継続行あり（78.1 MiB・半分がスタックトレース） |
|---|---|---|
| 現行（1 書式ぶんのバイト判定） | 343ms | 181ms |
| 正規表現 1 本を全行に適用 | 817ms | 469ms |
| 正規表現 + 先頭 1 バイトの門番 | 825ms | 403ms |
| 行ごとに 5 書式試す（1 つ目で一致） | 344ms | 197ms |
| 行ごとに 5 書式試す（5 つ目で一致） | 376ms | 203ms |

解析単体では +474ms なのに、取り込み全体では +159ms しか増えない。解析は
書き込みスレッドと重なって進むため、増えた分がそのまま全体に乗らない。

継続行が多いログでは、先頭 1 バイトが数字かどうかを見るだけで 14% 戻せる
（469ms → 403ms）。行を UTF-8 デコードしてから正規表現にかける手間を、継続行では
省けるため。**今回は入れていない**。門番の条件は書式ごとに違い、利用者に書かせると
定義が増える。5% の差にその複雑さを足す根拠が無い。

9 章で「行ごとに複数書式を試さない」と決めた判断は変えていない。上の表では
5 書式を試しても +10% 程度に見えるが、これは組み込み書式がバイト数個で弾けるため。
利用者定義の書式が候補に入ると、外れる書式のぶんだけ全行のデコードと正規表現照合が
積み上がる。**取り込み開始時に 1 つへ確定させる前提は保つこと**。

### 11.4 暴走する正規表現

利用者が書いた正規表現は、入れ子の量指定子で後戻りが爆発しうる。Java の `Matcher` は
外から止められないため、**行の長さに比例した回数しか文字を読ませない入力**
（`CustomLogFormat.BoundedCharSequence`、1 文字あたり 64 回・最低 4096 回）を渡し、
超えたら取り込みごと失敗させる。どの書式のどのファイルの何行目で止めたかを出す。

固まって返ってこない状態は避けられるが、正しい書式に直す必要があることは変わらない。
自動判定では巻き添えを避けるため、打ち切りに達した書式を候補から外して続行する
（そうしないと、書式ファイルを直すための画面すら開けなくなる）。

### 11.5 測り方

```bash

mvn -q -f <一時ディレクトリ>/aplv-java/pom.xml package -DskipTests
# 変更前後の jar を交互に実行する。APLV_HOME を分けて索引の置き場所も分離する
```

解析単体は `LogParser.parse` と正規表現を同じ行データに対して回して比べた
（`scratchpad/fmt/FormatBench.java`。リポジトリには入れていない）。
