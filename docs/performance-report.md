# インデックス構築・検索の性能調査レポート

対象: application-log-viewer（aplv） / MyBatis-log-viewer（mlv）
測定日: 2026-09-06 〜 2026-09-08
測定環境: Windows 11 / 12 論理コア / JDK 8 ターゲット / sqlite-jdbc 3.46.1.3
計測条件: `-Xmx2g`（1GB 級のログのみ `-Xmx3g`）、`tmp` は同一ドライブ

---

## 1. 要約

| | 対象 | 結果 |
|---|---|---|
| aplv 検索 | 1ページ目の応答 | 3,805ms → **22ms**（160万件） |
| aplv 構築 | 423MB / 300万件 | 15.4〜17.7秒 → **9.9〜12.0秒**（中央値で約 32% 短縮） |
| aplv DB | 同上 | 631MB → **566MB**（10% 削減） |
| mlv 構築 | 1084MB / 250万 SQL | 38.4秒 → **34.5秒**（約 10% 短縮） |
| mlv DB | 同上 | 834MB → **813MB**（2.5% 削減） |

最大の学びは **「同じ最適化が別アプリでは逆効果になった」** こと、そしてその原因が
行数や行幅ではなく **パイプラインのどちらが律速か** だったことである（→ 第5章）。

## 2. 計測方法

推測を避けるため、以下を原則とした。

1. **本番経路で測る** — `openOrCreate` + `buildIndex` を実際に呼ぶベンチを書く。
   スキーマだけ自前で組む版も用意し、索引の有無を切り替えて分解計測できるようにした。
2. **変更前後を同一データで測る** — `git worktree` で変更前の HEAD をビルドし、
   同じログファイルに対して交互に実行する。
3. **結果の同一性を確認する** — 新旧サーバを同時起動し、API 応答を突き合わせる。
4. **実行計画を見る** — `EXPLAIN QUERY PLAN` で索引選択と並べ直しの有無を確認する。

### ボトルネックの判定方法

**同じログ量をファイル数だけ変えて比較する。** パースは複数ファイルを並列処理し、
SQLite への書き込みは単一スレッドに集約されるため、ファイル数を増やして速くなれば
パース律速、変わらなければ書き込み律速と判定できる。

## 3. application-log-viewer

### 3.1 検索の遅さ（SQL 押し下げ）

**問題**: 全ヒットを `ResultSet` から Java オブジェクトに起こして件数を数え、
`offset`/`limit` を Java 側で適用していた。ヒット件数に比例した時間がかかる。

**対処**: 正規表現・grep がいずれも未指定なら、件数を `COUNT(*)`、ページを
`LIMIT/OFFSET` で SQL に任せる。

**結果**（160万件のインデックス、200件/ページ）:

| ケース | 前 | 後 |
|---|---|---|
| 全件 1ページ目 | 3,805ms | **22ms** |
| INFO 1ページ目 | 3,729ms | **39ms** |
| ERROR 1ページ目 | 108ms | **6ms** |
| ERROR 深い offset | 120ms | **6ms** |
| ERROR + 期間 | 77ms | **5ms** |
| WARN,ERROR | 398ms | **143ms** |

### 3.2 レベル絞り込みの並べ直し

`ORDER BY ts_millis` に対して SQLite が `idx_entries_level` を選ぶと、
ヒット全件を並べ直してから `LIMIT` を適用してしまう。3案を比較した（200万行）。

| ケース | 現状 | ANALYZE のみ | 複合索引 + ANALYZE |
|---|---|---|---|
| ERROR 1ページ目 | 93ms | 4ms | **3ms** |
| INFO 1ページ目 | 357ms | 0ms | **0ms** |
| ERROR 深い offset | 117ms | **254ms** ⚠ | **3ms** |
| 該当0件のレベル | 0ms | **318ms** ⚠ | **0ms** |
| ERROR + 期間 | 82ms | 2ms | **0ms** |

**`ANALYZE` 単体は安いが退行を伴う。** 統計だけ入れると全件走査を選ぶようになり、
深い offset とヒット0件で逆に遅くなる。複合索引 `(level, ts_millis, file_id, line_no)`
を足すと全ケースで速くなり退行がない。

### 3.3 冗長な索引の削除

複合索引の先頭列が `level` なので、`idx_entries_level(level)` は代替可能。
削除すると構築が速くなるだけでなく、**クエリも速くなった**。
幅の狭い索引が残っていると SQLite がそちらを選び、並べ直しが入るため。

| | 索引あり | 索引なし |
|---|---|---|
| 索引構築 | 4.82秒 | **3.25秒** |
| DB サイズ | 606MB | **566MB** |
| WARN,ERROR 1ページ目 | 331ms（`idx_entries_level` + SORT） | **17ms** |

### 3.4 構築のボトルネック特定

423MB / 300万件で、**単一ファイル 15.79秒・8ファイル 16.59秒とほぼ同じ**だった。
パースは並列化済みなので、律速は SQLite への書き込み側と判明。

分解計測（page_size 既定 4096）:

| | 取込 | 索引 | ANALYZE | 合計 | DB |
|---|---|---|---|---|---|
| 索引を取込中に維持 | 16.28秒 | — | 1.78秒 | 18.06秒 | 631MB |
| 索引を取込後に一括作成 | 7.40秒 | 6.18秒 | 1.40秒 | 14.98秒 | 615MB |
| 索引なし | 7.09秒 | — | 0.35秒 | 7.45秒 | 439MB |

行ごとの B-tree 更新が **9.2秒**、一括作成なら **6.2秒**。

### 3.5 PRAGMA のチューニング

**page_size**（索引は取込後に作成）:

| page_size | 取込 | 索引 | ANALYZE | 合計 |
|---|---|---|---|---|
| 4096（既定） | 7.88秒 | 6.61秒 | 1.52秒 | 16.01秒 |
| 8192 | 6.59秒 | 5.36秒 | 1.33秒 | 13.28秒 |
| **16384** | 6.24秒 | 5.01秒 | 1.44秒 | **12.69秒** |
| 32768 | 7.21秒 | 5.27秒 | 1.49秒 | 13.97秒 |

**analysis_limit**（`ANALYZE` が走査する行数の上限）:

| 設定 | ANALYZE | 合計 |
|---|---|---|
| 無制限 | 1.55秒 | 13.53秒 |
| 400 | 0.04秒 | 12.07秒 |
| **1000** | 0.04秒 | **11.61秒** |

**ただしサンプリングは統計の精度を落とす。** 低カーディナリティな先頭列では
「1 値あたりの行数」が `analysis_limit + 1` の定数になり、実データを反映しない。
値を上げても定数が変わるだけで精度は上がらない。

| 索引（先頭列） | 完全 ANALYZE | limit=100 | limit=1000 | limit=10000 |
|---|---|---|---|---|
| `level`（aplv・200万行） | 500000 | — | **1001** | — |
| `mapper`（mlv・50万行） | 62500 | 101 | **1001** | 10001 |
| `sql_type`（mlv・50万行） | 125000 | 101 | **1001** | 10001 |
| `ts_millis`（高カーディナリティ） | 1 | 1 | 1 | 1 |

それでも採用しているのは、**歪みがプラン選択を変えるかどうかは索引構成しだい**で、
aplv では変えないため。時刻順に辿れる索引が用途ごとに 1 本ずつしかなく競合しない。
200万行で 7 種のクエリ形状すべてについて、実行計画・実行時間が完全統計と一致した。

mlv は事情が異なり、`idx_entries_elapsed` が `idx_entries_type_ts` と競合するため、
`sql_type` + `elapsed_ms` の COUNT で計画が分かれる（どちらが速いかはデータ分布しだい）。
一覧・ページングの主要な形状は一致する。完全統計のコストが構築時間の約 5% にあたるため、
この偏りを許容して採用している。

**索引を増やすときは、この前提が崩れていないか `EXPLAIN QUERY PLAN` で確認すること。**

### 3.6 採用しなかったもの

| 案 | 測定結果 | 判断 |
|---|---|---|
| `cache_size` 増（64→128→256MiB） | 13.72 / 13.53 / 13.17秒 | 誤差レベル。メモリを使う価値なし |
| `journal_mode = OFF` | 11.00秒 vs MEMORY 11.91秒 | 再現しない差。耐障害性の議論を招くだけなので不採用 |
| `entries(file_id, line_no)` 索引 | — | UI が必ず timestamp を送るため到達しない経路のためのコスト |

### 3.7 最終結果（本番経路・変更前後を交互に3回）

| | 前 | 後 |
|---|---|---|
| 単一ファイル | 15.38〜15.82秒 | **10.57〜11.19秒** |
| 8ファイル | 16.18〜17.67秒 | **10.97〜11.97秒** |
| DB サイズ | 631 / 641MB | **566 / 573MB** |

コスト: 索引更新込みの INSERT が 200万行あたり +1.8秒、DB +21%（複合索引の追加分）。
差し引きで上表の短縮となる。

## 4. MyBatis-log-viewer

### 4.1 そのまま移植したら遅くなった

aplv の変更一式（page_size + 索引の後付け + analysis_limit）を移植したところ、
**216MB / 50万 SQL で 6.2秒 → 7.6秒**と約 20% 悪化した。

### 4.2 分解計測

| 216MB / 50万件 / 索引4本 | 取込 | 索引 | 合計 |
|---|---|---|---|
| 索引なし | 6.08秒 | — | 6.08秒 |
| 索引を取込中に維持 | 5.85秒 | — | **5.85秒** |
| 索引を取込後に一括作成 | 5.71秒 | 1.19秒 | 6.90秒 |

索引維持のコストがほぼ無く、一括作成は 1.19秒 かかるため、後付けは負ける。

> **この表は単発測定で、後にばらつきの大きさが問題になった。** 「索引なし 6.08秒」が
> 「索引を維持 5.85秒」より遅いのは物理的にありえず、この規模で 0.2〜0.3秒 の
> ばらつきが乗っていることを示している。結論（一括作成を採らない）は 2 案の差が
> 0.9秒 あるので揺るがないが、個々の数値を精度のあるものとして引用してはいけない。
> パーサ最適化後に 7 回ずつ測り直した値は 4.4 節に載せた。

### 4.3 採用したもの

| 変更 | 効果 |
|---|---|
| `analysis_limit = 1000` | `ANALYZE` が 1.94秒 → **0.13秒**（250万件） |
| `ensureStatistics` 廃止 → 毎回 `updateStatistics` | 索引構成の変更で古くなる統計を解消。上記で安くなったため可能に |
| `page_size = 16384` | 構築時間はほぼ横ばい、DB が **2.5% 削減**（834MB → 813MB） |

**結果**: 1084MB / 250万 SQL で 38.4秒 → **34.5秒**。

### 4.4 見送ったもの

- **索引の取込後一括作成** — 50万件で 6.2→7.6秒、250万件でも 34.5→35.6秒と一貫して悪化。
  パーサ最適化で書き込み律速に移ったあとも変わらない。50万件・1ファイルで各 7 回測ると
  中央値は 索引なし 3.39秒 / 取込中に維持 3.67秒 / 取込後に一括 4.50秒。
  この規模では索引 B-tree がページキャッシュ（約 64MiB）に収まるため行ごとの維持は
  +0.28秒 で済む（ばらつき幅 0.25秒 と同程度なので精度は低い）のに対し、
  一括作成は幅の広い表を索引 4 本ぶん走査するため +0.83秒 かかる（範囲が重ならず明確）
- **一覧 `raw` の切り詰め** — `MAX_LIMIT` の既存コメントに
  「raw を切り詰めるとハイライトとずれるため上限側で抑える（5000件で 5.2MB 実測）」
  と実測付きの判断が既にあり、`MAX_LIMIT=1000` で対処済みのため踏襲

## 5. なぜ同じ最適化で結果が逆になったのか

### 5.1 主因: パイプラインのどちらが律速か

同じログ量をファイル数だけ変えて、索引なしの取込を比較した。

| | 1ファイル | 8ファイル | 判定 |
|---|---|---|---|
| aplv（300万件） | 7.09秒 | 7.02秒 | **書き込み律速** |
| mlv（50万件） | 5.60秒 | **2.28秒**（2.5倍） | **パース律速** |

aplv のパーサは「1行 = 1エントリ」でバイト列の事前判定も入っており軽い。
対して mlv は Preparing / Parameters / Total の **3行を1ブロックに組み立てる**うえ、
正規表現とパラメータ抽出が入り、1エントリあたり約 5 倍重い。

**書き込みスレッドに余力があるうちは、索引維持のコストは隙間に隠れてタダになる。**
取込後の一括作成はその余力を使えず、純粋な直列の追加時間になる。

### 5.2 検証: 律速を変えると符号が反転する

mlv で同じ 50万件をファイル数だけ変えると、隠れていた索引維持コストが露出する。

| mlv 50万件 | 索引なし | 取込中に維持 | 取込後に一括 |
|---|---|---|---|
| 1ファイル（パース律速） | 6.08秒 | **5.85秒**（維持 ≒ 0） | 6.90秒 |
| 8ファイル（書き込み律速） | 2.54秒 | 4.11秒（維持 1.57秒） | **4.07秒** ← 拮抗 |

さらに行数を上げると予測どおり逆転した。

| mlv 8ファイル・240万件 | 索引なし | 取込中に維持 | 取込後に一括 |
|---|---|---|---|
| | 8.72秒 | 16.79秒（維持 8.07秒） | **16.16秒** ← 後付けが勝つ |

### 5.3 副次要因

- **行数** — 書き込み律速でも行数が少なければ拮抗する（50万件で 1.57 vs 1.43秒）。
  行数が増えると索引 B-tree がページキャッシュ（64MiB）を超えて逐次更新が悪化し、
  ソートベースの一括作成が有利になる。
- **行幅** — mlv は 209 B/行、aplv は 146 B/行。一括作成は表を全走査するため、
  行が太いほど不利。同じ 240〜300万件でも改善幅は aplv **−25%**、mlv **−4%** と縮む。

### 5.4 追記 — パーサ側を削ると律速は移る

主因がパースだと分かったので、mlv のパーサを詰めた。ヘッダ行の解析で
スレッド判定の正規表現（`THREAD_HINT`）を 2 回無条件に実行していたが、
`^main` 以外のすべての選択肢は `-` を含むため、**`-` が無く "main" でも始まらない
文字列は正規表現を呼ばずに不一致と判定できる**（判定結果は同一）。
FQCN の logger がこれに当たるため、失敗すると分かっている走査を丸ごと省ける。

| 90万行のヘッダ解析 | 時間 |
|---|---|
| 現状（`THREAD_HINT` を常に 2 回） | 1.72 秒 |
| `-` と `main` で事前判定 | **0.25 秒** |
| 正規表現を一切呼ばない（下限） | 0.15 秒 |

この 1 箇所で、`LogParser.parse` の 91% を占めていたコストが消えた。

| 索引なしの取込・50万件 | 1ファイル | 8ファイル | 判定 |
|---|---|---|---|
| 最適化前 | 6.90 秒 | 2.23 秒 | パース律速（3.1 倍） |
| 最適化後 | 3.50 秒 | 2.12 秒 | パース律速は緩和（1.65 倍） |

索引込みの構築では **6.49 秒 → 3.93 秒（39% 短縮）** となり、8 ファイル時（3.85 秒）と
同水準に達した。つまり **mlv は書き込み律速に移り、これ以上パーサを削っても
構築時間は縮まない**。

aplv にも同じ最適化を入れたが、元から書き込み律速なので構築時間は変わらない
（11.4〜12.3 秒 → 11.0〜11.5 秒で誤差の範囲）。CPU は減るので入れてある。

**律速は最適化で移動する。** 一度判定したら終わりではなく、効いたあとに測り直す。

### 5.5 結論

> **「索引は取込後にまとめて作る方が速い」は無条件の定石ではない。**
> 書き込みが律速で、かつ行数が多いときにだけ成立する。
> パースが律速なら索引維持はタダなので、後付けは必ず損になる。

## 6. 一般化できる指針

1. **最初にボトルネックを特定する。** 同じ入力をファイル数だけ変えて測れば、
   パース律速か書き込み律速かが一発で分かる。ここを飛ばすと、効かない場所を
   最適化して悪化させる（実際に mlv で 20% 悪化させた）。
2. **移植先で測り直す。** 姉妹プロジェクトで 30% 効いた手法が、別プロジェクトでは
   逆効果だった。コードが似ていても律速が同じとは限らない。
3. **統計は入れるだけでは足りない。** `ANALYZE` 単体では退行するケースがあり、
   索引と組み合わせて初めて全ケースで速くなる。実行計画まで確認する。
   `analysis_limit` によるサンプリングは低カーディナリティ列の統計を定数に潰すため、
   「安いから入れておく」ではなく、索引構成ごとに影響を確認して採否を決める。
4. **冗長な索引は構築だけでなく検索も遅くする。** 幅の狭い索引が残っていると
   プランナがそちらを選び、並べ直しが発生することがある。
5. **性能に関するコメントは測ってから書く。** この調査中、実測と食い違う説明を
   4回書いてレビューで指摘された（複数レベルの実行計画、page_size の効果、
   mlv で後付けを見送った理由、analysis_limit の精度）。推測を断定形で書かない。
6. **判断の根拠にする数値は複数回測る。** 数百 MB 規模では 1 回の測定に数 % の
   ばらつきが乗る。単発の差がその範囲に収まるなら「差は無い」と書く。試行回数と
   代表値（中央値か最小値）を添えれば、後から読む人が精度を見積もれる。
7. **既存コメントに記録された判断を確認する。** mlv では `raw` の切り詰めが
   実測付きで既に否定されていた。理由なく覆さない。

## 7. 再現方法

### ベンチマークの構成

本番経路をそのまま呼ぶ形にする。

```java
IndexStore.deleteIndexFiles(dir);
List<Path> paths = Discovery.findLogFiles(dir);
long t0 = System.nanoTime();
try (Connection conn = LogIndex.openOrCreate(dir)) {
    LogIndex.BuildResult r = LogIndex.buildIndex(conn, paths, null);
    // 経過時間・DB サイズ・索引一覧・page_size を出力
}
```

索引の有無で分解したい場合は `openOrCreate` を使わず、テーブルだけ自前で作って
`buildIndex` を呼ぶ。`buildIndex` はスキーマを作らないため、索引の有無を制御できる。

### 変更前後の比較

```bash
git worktree add <一時ディレクトリ> HEAD
mvn -f <一時ディレクトリ>/…/pom.xml clean package -DskipTests
# 変更前の jar と変更後の jar を同じログに対して交互に実行する
```

インデックスの保存先は環境変数（aplv は `APLV_HOME`、mlv は `MLV_HOME`）で
分けられるため、新旧サーバを同時起動して API 応答を突き合わせられる。

### 実行計画の確認

```sql
EXPLAIN QUERY PLAN
SELECT … FROM entries e JOIN files f ON e.file_id = f.id
WHERE e.level IN (?) ORDER BY e.ts_millis, e.file_id, e.line_no LIMIT 200;
```

`USE TEMP B-TREE FOR ORDER BY` が出ていれば並べ直しが発生している。
